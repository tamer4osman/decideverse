## 3. Exact cause of the WASM lifecycle leak

The reviewed adapter exposed `recreate: init`. `init()` unconditionally
executed `kernel = await src.OmniDecide.create(config)` — overwriting the
only reference to the previous kernel **without calling its `free()`**.
`shutdown()` released only the *current* handle, so the handle abandoned by
a recreation stayed registered in the C wrapper's slot table
(`g_kernels[]`, `g_kernel_live++` in `odkw_kernel_create`) forever: it was
unreachable from JavaScript but still counted as live. Reproduced against
the real WASM module before the fix:

| Operation (old adapter) | Live kernel handles (`odkw_kernel_count`) |
|---|---:|
| First initialization | 1 |
| Recreate with new settings | 2 |
| Shutdown, then initialize again | 2 |

With 64 kernel slots in the wrapper, repeated settings changes would
eventually exhaust the registry (`odkw_kernel_create: handle registry
exhausted`).

## 4. Lifecycle implementation and cleanup behavior

States: `uninitialized` → `initializing` → `ready` ⇄ `recreating` →
`shutting-down` → `uninitialized`; `error` for initialization failures.
Documented in `gamelab/docs/ADAPTER.md`.

- **init()** — valid from `uninitialized`/`error`; while a transition runs
  the same in-flight promise is returned; while `ready` it is **explicitly
  rejected** (points to `recreate()`), so repeated initialization can never
  allocate a second handle.
- **recreate()** — valid only from `ready`; validates the configuration,
  creates the replacement with the real API, **confirms** it, releases the
  previous instance, then swaps the managed handle and metadata. On
  creation failure the previous kernel stays genuinely `ready` with its
  previous configuration and the result reports `recreated:false` +
  `RecreationFailed` (kernel status preserved) — readiness is never faked.
- **shutdown()** — releases the managed handle, clears the reference,
  returns to `uninitialized`; idempotent (repeat = no-op, no double free);
  decisions afterwards are rejected before the kernel (`AdapterNotReady`).
- **Epoch guard** — every transition bumps a lifecycle epoch; a create that
  resolves after a shutdown/recreate race disposes its own handle
  immediately and never becomes visible.
- **Cleanup failures are never swallowed** — a throwing `free()` is counted
  (`lifecycleStats.cleanupFailures`), reported (`engine:cleanup-error`,
  result `cleanupError`), and logged; the original error of the operation
  is preserved alongside it.
- **UI** — Settings offers *Apply engine settings (re-create)*, *Release
  engine (shutdown)*, *Initialize engine* and shows real accounting
  (kernels created/released, recreations/failures, cleanup failures, live
  managed kernels). The engine pill and dashboard render the new states.

## 6. Action-history fix

`session.actionLog` is now the single authoritative record of **successful
player actions** (`begin`, `investigate`, accepted `decide`, `accuse`,
`close-unsolved`), written exactly once per accepted command by the game
module. The workspace renders `session.actionLog.length`, so display and
data cannot disagree. Kept strictly separate (documented + tested): player
actions vs simulation events vs OmniDecide invocations vs kernel results.
A rejected command emits an event only; a failed engine invocation is
recorded as a failed decision, never as a player action. The game's
`runLog` retains its own documented purpose (the faithful replay input
sequence, including failed decision attempts); the two records differ by
exactly the number of failed attempts — asserted by tests.

## 7. Seed consistency fix

The briefing seed is validated (non-numeric → default `20261108`; numeric
→ unsigned 32-bit) and written to the authoritative session via
`session.setSeed()` (which also rebuilds the RNG streams), then used for
scenario initialization, displayed by the workspace, recorded in history,
retained by reset, and reused by replay. UI and simulation can no longer
disagree about the seed.

## 8. Reset and replay verification

- Reset: rebuilds the scenario from the **same** effective seed, clears
  the shared action counter (new run, documented semantics), keeps the
  previous run replayable (`lastRun`), keeps history intact.
- Replay: re-executes the recorded `runLog` through the pure reducer with
  the recorded seed and **genuinely re-submits** rebuilt requests to the
  real kernel — the browser suite asserts `5/5` byte-identical envelopes,
  the same ending, and that the replayed final state is identical
  (Node suite: full JSON equality). Replay never appends to the action
  counter. Replay is honestly labeled a GameLab simulation capability,
  not a kernel feature and not a recorded-result playback.

## 14. Known limitations

- Hosted CI execution and the actual PR require repository credentials —
  not available in this environment (see §12).
- The adapter reports the module-wide kernel count only while it manages a
  handle (`engineCount() === null` after shutdown); post-shutdown counting
  uses the documented probe strategy in tests.
- Replay of a run containing a *failed* decision deterministically aborts
  at that attempt (documented in LIMITATIONS.md).
- Node-level action-tracking tests run the real module against a minimal
  DOM shim; full-fidelity UI behavior remains covered by the Playwright
  suite (which runs the real browser DOM).
- The browser E2E drives the invalid-action case via a stale-node double
  submit (the same path a fast double-click takes); buttons are otherwise
  disabled by the UI, which is correct behavior.
