## 3. Actual cause of the failed-cleanup handle leak

In the Stage 2.1 adapter, `recreate()` released the previous instance
via `releaseKernelInstance(previous, 'recreate')`, which **caught** a
throwing `free()`, counted it, reported it — and returned an error
descriptor while the caller proceeded to `kernel = created`. The only
JavaScript reference to the old kernel was the `previous` local, which
went out of scope. The same reference-dropping pattern existed in
`shutdown()` (kernel nulled before the release attempt) and
`disposeKernel()` (stale-create disposal). The C wrapper never lost the
handle: `odkw_kernel_create` registers it in `g_kernels[]` and
`odkw_kernel_free` only clears the slot when it actually runs — so a
`free()` that never completed left the handle live in `g_kernels[]`
(`g_kernel_live` still counting) but unreachable from the adapter.

Reproduced against the **real WASM module** before the fix
(`repro` sequence: init → recreate with an old-instance `free()`
failure → decision → shutdown):

| Measurement | Result |
|---|---:|
| Handles after recreation | 2 |
| Cleanup failures recorded | 1 |
| Handles after adapter shutdown | 1 |
| Old handle released | **No** |
| Adapter accounting | `created: 2, released: 1` — one handle permanently unreachable |

The previous lifecycle tests masked this because their fixture manually
released the orphaned handle through the underlying registry before
asserting; the adapter itself never owned the recovery.

## 4. Adapter ownership and pending-cleanup design

Every kernel handle the adapter allocates is owned **exactly once**:

- the active instance (`lifecycleStats.activeHandles` ∈ {0,1}), or
- a pending-cleanup entry (`lifecycleStats.pendingCleanup`), or
- confirmed released (`lifecycleStats.released`).

Exact invariant, asserted by the suite at every scenario boundary:
`created === released + activeHandles + pendingCleanup`.

The ownership registry is **internal to the adapter** (a private
`pendingCleanup` array; the public surface exposes only sanitized
diagnostics — `pendingCleanupDetail` = `[{ reason, attempts, state,
sinceMs, error }]`, no kernel references). A failed `free()` registers
the handle with its original error, the failing operation as `reason`,
an attempt count and a timestamp; the reference is never dropped.
Transient stale creates (epoch-race disposals) are accounted identically
(`created` includes them; their disposal failures land in the same
registry).

Events (additive): `engine:cleanup-pending`, `engine:cleanup-recovered`,
`engine:shutdown-incomplete` (existing events unchanged).

## 5. Safe retry behavior

Release-evidence rules, derived from the verified C implementation:

1. A **non-throwing `free()`** is release evidence. `odkw_kernel_free`
   (src/wrappers/odk_wasm.c:235) resolves the registry slot, clears it
   (`g_kernel_live--`) and only then destroys the kernel; a call on an
   already-cleared slot is a no-op. Therefore a non-throwing call always
   ends with the handle not allocated — released by this call, or
   already released before — and a retry **can never double-free**.
2. The wrapper's **`closed` flag** (set only after a completed release)
   resolves an entry **without any further call** — no destructive
   operation is performed on an instance that may already be destroyed.
3. If a retry throws again, the entry stays owned: error and attempt
   count are updated, the unresolved state keeps being reported.
   `retryCleanup()` during an in-flight transition reports
   `deferred: true` instead of racing it.

**Documented engine-API limitation:** the public API exposes no
per-handle existence query (only the module-wide `odkw_kernel_count`).
While a release keeps failing, the adapter therefore cannot externally
verify *which* handle is live; it retains ownership conservatively and
reports unresolved state rather than claiming an unevidenced release.
The module-wide count is used as a supporting diagnostic
(`engineCount()` is readable through any owned handle, active or
pending), never as per-handle proof.

## 6. Recreation and shutdown behavior

**Recreation** (create-first, release-after, Stage 2.1.1 ordering):
validate config → recover pending entries → if unresolved handles remain,
**defer** (`recreated:false`, error kind `PendingCleanupUnresolved`, no
allocation — the policy that makes unbounded accumulation impossible) →
create replacement → confirm → release previous (failure ⇒ pending
registry + `cleanupPending:true` in the result; the degraded state is
never reported as fully clean) → swap handle and metadata.

**Shutdown**: release active handle (failure ⇒ pending registry) →
retry every pending entry → aggregate → `shutdownComplete` /
`incompleteShutdown` + `pendingCleanupDetail` in the result; repeated
invocations retry remaining entries (idempotency = no double free, not
skipping unfinished cleanup) and a fully-successful shutdown leaves zero
adapter-owned live handles.

**Initialization**: recovers pending entries first and is deferred
(`PendingCleanupUnresolved`) while any remain.

## 16. Remaining limitations

- Hosted CI execution and the actual pull request require repository
  credentials — not available in this environment (§14).
- The engine API provides no per-handle existence query; while a
  release keeps failing, unresolved state is reported conservatively
  instead of a per-handle claim (§5, documented in ADAPTER.md and
  LIMITATIONS.md).
- A `free()` that throws *inside* the C kernel destruction (after the
  registry slot was cleared) leaves the kernel memory partially
  destroyed — not observable or repairable from JavaScript; the retry
  in that case is a safe no-op and the accounting stays correct. In the
  compiled module this path is not expected in normal operation.
- Replay of a run containing a failed decision deterministically aborts
  at that attempt (Stage 2.1 limitation, unchanged).
